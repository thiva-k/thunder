# Register an MCP Client from Its Metadata Document

Register an MCP client from its Client ID Metadata Document (CIMD) when its vendor publishes one. The client's ID is an HTTPS URL on the vendor's domain, and that URL serves the client's name, redirect URIs, and how it authenticates. You review what the document declares, and <ProductName /> creates the application from it. You do not enter redirect URIs or credentials yourself.

<ProductName /> reads the document only when you register or re-fetch the client. When a user signs in, the client authenticates like any other application.

If the application's sign-in flow asks the user for consent, the consent screen also shows the host that publishes the client and the host that the client returns to. A host with non-ASCII characters appears in its ASCII form, usually with punycode labels that start with `xn--`, so it cannot pass for a host that looks the same. When the client returns to `localhost`, `127.0.0.1`, or `::1`, the screen warns the user that other programs on their device can use the same address and tells them to continue only if they started the application.

## Prerequisites

- <ProductName /> is running. See [Get Started](../../../../getting-started/get-thunderid).
- You can sign in to the <ProductName /> Console.
- For a client without a tile in the Console, its metadata document URL.

<Stepper stepNode="h2" as="h2">

## Start the Application Wizard

1. Sign in to the <ProductName /> Console.
2. Navigate to **Applications** and click **Add application**.
3. Select **MCP client**.
4. If prompted, select an organization unit and click **Continue**.

## Choose the Client

On **Which MCP client are you connecting?**, do one of the following:

- **For Claude, ChatGPT, or Visual Studio Code**, click its tile. <ProductName /> creates the application straight away and opens it.
- **For any other client**, select **Another client with a CIMD**, enter its document URL, and click **Fetch document**. Review the preview, click **Continue**, adjust the name on the Details step if needed, and click **Finish**.

</Stepper>

## Review and Update the Client

Open the application's **General** tab. A **CIMD** section shows the values taken from the document, read-only. Configure everything else, such as allowed user types and the sign-in flow, as you would for any other application.

When the vendor changes its document, <ProductName /> does not pick up the change on its own. Click **Re-fetch document**, review the changes, click **Apply**, and then **Save**. Re-fetching applies the authorization code and refresh token grant types the document declares, and keeps the other grant types the application already holds while the document's authentication method still allows them. If the document now makes the client public, re-fetching removes token exchange and JWT bearer and turns off identity assertions.

## Use Identity Assertions (ID-JAG)

A client whose document declares the `private_key_jwt` authentication method can use identity assertions (ID-JAG) with <ProductName /> in either direction:

- **To request identity assertions** for an external authorization server, open the **Advanced** tab and turn on **Identity assertions (ID-JAG)**. This also adds the token exchange grant type, which such a client can use only to request identity assertions. See [Issue Identity Assertions (ID-JAG)](../../../protocols/oauth-oidc/identity-assertion-grant/issue-identity-assertions).
- **To redeem identity assertions** from a trusted identity provider, open the **Advanced** tab and add the **JWT bearer** grant type. See [Accept Identity Assertions from an External IdP](../../../protocols/oauth-oidc/identity-assertion-grant/accept-identity-assertions).

Registering the client never adds these grant types, even when its document declares them, so you choose them here. The client's ID is its document URL, so an identity assertion issued for it carries that URL as its `client_id`. An authorization server that also identifies the client by its document URL recognizes it without any client ID mapping.

On the **Advanced** tab, **Client authentication method**, **Public client**, and **PKCE required** come from the document and cannot be changed. The only grant types offered are authorization code, which stays on, refresh token, JWT bearer, and token exchange, which comes and goes with identity assertions. A public client, whose document declares `none`, cannot use token exchange, JWT bearer, or identity assertions.

## Let Clients Sign In Without Registering Them

Instead of registering each client, you can create one application or agent that admits every client whose metadata document URL is on a domain you trust. <ProductName /> stores nothing for these clients. When one starts signing in, <ProductName /> finds the application or agent whose trusted domains match the client's URL, retrieves the document, applies the same document rules as for a registered client, and signs the user in with that application's or agent's settings. The sign-in and consent pages show the client's own name and logo from its document.

To admit clients that act for the signed-in user, create an application:

1. In the <ProductName /> Console, navigate to **Applications** and click **Add application**.
2. Select **CIMD**, and if prompted, select an organization unit and click **Continue**.
3. On **Which clients should sign in?**, select **Any client from trusted domains**.
4. Enter each domain whose clients you trust, such as `claude.ai` or `vscode.dev`. Enter `*.example.com` to trust every subdomain of `example.com`, but not `example.com` itself. Click **Continue**.
5. Enter a name for the application and click **Finish**.

To admit AI agents instead, navigate to **Agents**, click **Add agent**, and under **How the agent signs in** select **As any client from trusted domains** and enter the domains.

Then turn the feature on for the deployment:

1. Navigate to **Configurations** and open the **Client ID Metadata Documents** tab.
2. Turn on **Unregistered clients**.

Configure everything else, such as the sign-in flow, allowed user types, and design, on the application or agent as usual. Every client it admits uses those settings. To change the domains later, open the application's **Trusted domains** tab, or the agent's **Credentials** tab.

How trusted domains apply:

- A registered application or agent with the same client ID always takes precedence over trusted domains.
- A domain can be trusted by only one application or agent. When several domains match a client, the most specific one applies: an exact domain before a wildcard, and a longer wildcard before a shorter one.
- <ProductName /> asks for consent separately for each client, so a user's consent to one client is never taken as consent to another client of the same application or agent.
- <ProductName /> keeps a retrieved document for as long as its `Cache-Control` header allows, from 1 minute to 1 hour, or 5 minutes when the header sets no lifetime. A document that cannot be retrieved, or that breaks a document rule, stops the client from signing in.
- To stop one client without changing its domains, add its document URL under **Blocked clients** on the **Client ID Metadata Documents** tab of **Configurations**.
- Turning off **Unregistered clients**, removing a domain, or deleting the application or agent stops its clients from signing in and from refreshing their tokens. Access tokens already issued stay valid until they expire.

:::caution
Trusting a domain admits every client that anyone can publish under it. Add only domains whose publishers you trust, and prefer an exact domain to a wildcard.
:::

These clients follow the same redirect URI rules as registered ones. A loopback redirect URI, such as `http://127.0.0.1/callback`, matches on any port, so native clients that listen on a random port, such as Claude Code, can sign in.
